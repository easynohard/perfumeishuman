# 0020. 약관·처리방침 개정 시 재동의 — 거부하면 탈퇴 안내

- Status: **Superseded by [0022](./0022-defer-reconsent-from-mvp.md)** (2026-10-28) — MVP에서는 도입하지 않기로 했다. 아래 내용은 **향후 도입 시 설계안**으로 보존한다
- 관련 문서: [02-user-stories.md](../02-user-stories.md) F1·F2·F3, [04-wireframes.md](../04-wireframes.md) §3·§4.2, [0008-anonymized-retention-on-withdrawal.md](./0008-anonymized-retention-on-withdrawal.md), [0010-minimal-personal-data-collection.md](./0010-minimal-personal-data-collection.md), [07-api-spec.md](../07-api-spec.md) §2

## Context

약관·처리방침은 버전을 갖고(E8 `policyversion`), 가입 시 동의한 버전이 기록된다(E7 `confirmhistory`). 약관이 개정되면 이미 가입한 회원이 새 버전에 동의했는지가 문제가 된다. 02 F2는 "개정 시 시행일 전 공지"까지만 정했다. 이메일을 수집하지 않으므로(ADR 0010) 공지는 서비스 내 게시이고, 개별 통지 수단이 없다. 7단계 API 설계 중 재동의 방식을 정해야 했다.

## Decision

1. **약관·처리방침의 새 버전이 시행되면 기존 회원에게 재동의를 받는다.**
2. 재동의는 **화면이 아니라 모달**이다(화면 16개 유지). 시행 후 회원이 로그인 상태로 접속했을 때 뜬다. 새 버전의 요지와 `/terms`·`/privacy` 링크를 함께 보여준다.
3. **동의하면** `POST /me/consents`로 새 버전·동의 시각이 `confirmhistory`에 추가 기록된다(기존 이력은 보존, 동의 경로는 재동의로 구분).
4. **거부하면** 즉시 탈퇴시키지 않고 **탈퇴를 안내한다.** 04 §4.2의 탈퇴 확인 모달(익명 보존 고지 포함)로 연결한다.
5. 재동의가 끝나지 않은 동안 회원 기능(시향기 작성·추천·닉네임 변경 등)은 쓸 수 없고, 열람은 계속 가능하다. 해당 API는 403 `CONSENT_REQUIRED`로 응답한다.
6. 상태는 `GET /me`의 `pending_consent`로 내려준다(없으면 `null`).

## 검토한 대안

- **개정 공지만 하고 계속 이용 시 동의로 간주**: 구현이 가장 단순하지만 개인정보 처리 변경에 대한 명시적 동의 증빙이 약하다. 사용자가 재동의를 받기로 해서 기각.
- **거부 시 즉시 강제 탈퇴**: 되돌릴 수 없는 처리(ADR 0008)를 사용자의 의사 확인 없이 실행하게 되어 기각.

## Consequences

- (+) 동의 증빙이 버전별로 남는다.
- (+) 새 화면 없이 모달과 API 2개(`GET /me` 필드, `POST /me/consents`)로 처리된다.
- (−) **04 와이어프레임에 재동의 모달이 없다.** 8단계 UI 상세에서 문구·형태를 확정하고 04 §3에 반영해야 한다. 02 F2 AC에도 재동의가 빠져 있다.
- (−) 개정 때마다 전 회원에게 재동의를 요구하게 된다. 오탈자 수정 같은 경미한 개정은 구분하고 싶다면 `policyversion`에 재동의 필요 여부 필드가 필요하며, 그때는 ERD 변경과 함께 새 ADR을 쓴다.
- (−) 재동의 모달이 쓰기 전환에 마찰을 더한다(N2·N3). 개정 빈도를 낮게 유지해야 한다.
