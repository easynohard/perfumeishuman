# 0017. API 설계 원칙 — REST·세션 쿠키·오프셋 페이지네이션

- Status: **Accepted** (2026-10-03 확정)
- 관련 문서: [07-api-spec.md](../07-api-spec.md) §1, [0005-seo-slug-urls.md](./0005-seo-slug-urls.md), [0008-anonymized-retention-on-withdrawal.md](./0008-anonymized-retention-on-withdrawal.md), [0010-minimal-personal-data-collection.md](./0010-minimal-personal-data-collection.md), [0011-soft-delete-reviews.md](./0011-soft-delete-reviews.md), [0012-identifier-formats.md](./0012-identifier-formats.md), [0016-aggregate-update-and-soft-delete-scope.md](./0016-aggregate-update-and-soft-delete-scope.md)

## Context

7단계(API 명세)는 엔드포인트를 도출하기 전에 모든 엔드포인트에 공통으로 적용될 원칙을 정해야 한다. 이 원칙들은 한번 프론트엔드가 쓰기 시작하면 바꾸기 어렵고, 일부(인증 방식)는 9단계 기술 스택 선택에도 영향을 준다. 이 서비스의 조건은 다음과 같다.

- 웹 전용 서비스이며 별도 모바일 앱 계획이 없다. 1인 운영, 소규모(향수 100~300개)다.
- 탈퇴(ADR 0008)와 관리자 차단은 **즉시 반영**되어야 한다.
- 비용을 최소화하려는 의도로 serverless를 우선 검토한다. 개인정보는 **국내 리전에서만** 처리한다.
- 화면 URL이 이미 `/reviews/:slug` 등 REST 모양이라(ADR 0005) 같은 도메인에서 API 경로와 겹칠 수 있다.

## Decision

### 1. URL: REST 스타일 + `/api/v1/` 접두사

- 자원은 명사 복수형으로 표현하고, 동작은 HTTP 메서드(GET·POST·PATCH·DELETE)로 구분한다. 조회(GET)로 상태를 바꾸지 않는다.
- 모든 API 경로에 `/api/v1/` 접두사를 붙인다. `/api`는 화면 URL과의 충돌을 막고, `/v1`은 나중에 호환이 깨지는 변경을 할 때를 위한 보험이다.
- 본인 자원은 `/me` 계열, 관리자 API는 `/admin` 계열로 분리한다. 경로 분리는 편의일 뿐이며 권한은 서버가 매 요청마다 검사한다.
- 공개 식별자는 ADR 0005·0012의 슬러그·랜덤 코드를 그대로 쓴다. 내부 순차 id는 노출하지 않는다.

### 2. 인증: 세션 쿠키

- 로그인 성공 시 서버가 세션을 만들고 `HttpOnly`·`Secure`·`SameSite=Lax` 쿠키로 세션 id만 전달한다.
- 쓰기 요청(POST·PATCH·DELETE)에는 CSRF 방어를 추가한다.
- 세션은 **서버 측 저장소**(DB 등)에 둔다. 구체 저장소는 9단계에서 확정한다.
- 탈퇴·관리자 차단 시 해당 사용자의 세션을 즉시 삭제하고, 요청마다 사용자 상태를 확인한다.

### 3. 권한: 4개 역할, 삭제분은 404

- 역할은 **비로그인 / 회원 / 관리자 / 탈퇴 회원**이다.
- 소프트 삭제된 시향기(ADR 0011)는 관리자 API 외의 어떤 응답에서도 존재하지 않는 것으로 취급하며, 직접 조회하면 **404**로 응답한다. 삭제된 글이 존재했다는 사실도 드러내지 않는다.

### 4. 에러 응답: HTTP 상태 코드 + 자체 형식

- 실패는 적절한 HTTP 상태 코드와 함께 `{ "error": { "code", "message", "fields" } }` 형식으로 응답한다. 모든 엔드포인트가 같은 형식을 쓴다.
- 서버 내부 정보(스택 트레이스·DB 오류)는 응답에 담지 않는다.

### 5. 페이지네이션: 전부 오프셋

- 목록 API는 모두 오프셋(페이지 번호) 방식을 쓴다. 기본 20개 단위다.
- 추천순 피드에서 보는 도중 순위가 바뀌면 "더보기" 때 같은 글이 다시 나오거나 빠질 수 있다. 이 점은 **감수한다**.

## 검토한 대안

- **토큰(JWT) 인증**: 서버가 상태를 안 가져 확장과 앱 연동에 유리하나, 만료 전 강제 로그아웃이 안 되어 탈퇴·차단 즉시 반영 요건과 충돌한다. 차단 목록을 조회하면 토큰의 장점이 사라진다. 토큰은 저장 위치(XSS)·갱신 설계 부담도 있다. 기각.
- **커서 방식 페이지네이션**: 추천순 피드의 중복·누락이 없으나, 관리자 목록의 페이지 점프가 불편하고 구현이 복잡하다. 사용자가 단순함을 우선해 기각. 피드만 커서로 하는 혼합안도 검토했으나 채택하지 않았다.
- **`/api` 접두사 없이 화면과 같은 경로 사용**: 같은 URL이 HTML과 JSON 두 역할을 하게 되어 구분 로직이 필요하다. 기각.
- **`/v1` 생략**: 지금은 우리 프론트만 쓰므로 필수는 아니다. 붙이는 비용이 거의 없어 보험으로 포함한다.
- **BaaS 내장 인증 사용**: 내장 인증이 이메일·프로필을 기본 저장하는 경우가 많아 ADR 0010(공급자 + 회원번호만 수집)과 충돌하고, 자체 토큰 방식이라 탈퇴 즉시 차단도 번거롭다. 호스팅 선택은 9단계 소관이지만 이 점을 선정 기준에 반영한다.

## Consequences

- (+) 모든 엔드포인트가 같은 인증·에러·페이지네이션 규칙을 따라 프론트 처리 코드가 단순해진다.
- (+) 탈퇴·차단이 세션 삭제로 즉시 반영된다.
- (+) 삭제분 404 규칙으로 ADR 0011·0016의 "삭제분 비노출"이 API 계약에 명시된다.
- (−) serverless를 택하면 세션을 외부 저장소에 두어야 하고, 요청마다 저장소 조회 비용이 든다.
- (−) 쓰기 요청마다 CSRF 방어를 구현해야 한다.
- (−) 오프셋 방식의 피드 중복·누락 가능성과, 뒤쪽 페이지로 갈수록 쿼리가 느려지는 문제가 있다. 이 서비스 규모에서는 문제 수준이 아니라고 판단하나, 트래픽이 커지면 재검토해야 하며 그때는 새 ADR로 대체한다.
- **9단계로 넘기는 제약**: 호스팅은 serverless 우선 검토, **국내 리전 필수**(개인정보 국외 이전·처리위탁 고지 부담 최소화), 비용 최소화. 세션 저장소·DB 연결 풀링·배치 스케줄러(ADR 0016의 집계 보정, ADR 0011의 완전 삭제)·무료 플랜의 상업 이용 제한을 선정 시 확인한다.
