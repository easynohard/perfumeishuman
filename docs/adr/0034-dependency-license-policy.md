# 0034. 의존성 라이선스 정책 — 허용형만 쓰고, 조건부는 검토 후 예외 등록, 코드 공개 의무·상업 제한·라이선스 불명은 금지

- Status: **Accepted** (2026-11-17 — 9단계 기술 스택 8번 결정 = 라이선스 감사 2차, 사용자 승인)
- 관련 문서: [quality/license-audit.md](../quality/license-audit.md)(1차) · [ADR 0025](./0025-typeface-and-icon-set.md) · [ADR 0031](./0031-font-icon-bundling-official-packages.md) · [ADR 0033](./0033-test-strategy-and-ci-quality-gates.md)(CI 라이선스 검사) · [01](../01-problem-definition-scope.md) W1(수익화)·N11
- **본 문서는 법률 자문이 아니다.** 공개된 라이선스 조건을 읽은 판단이며, 출시 전 관문의 최종 감사에서 다시 확인한다.

## Context

라이선스 감사 1차(8단계)는 디자인 에셋(서체·아이콘·이미지·색상)만 다뤘고, 의존성(npm 패키지) 감사와 허용/금지 라이선스 ADR을 9단계로 넘겼다. ADR 0033은 CI에 라이선스 검사를 넣되 기준을 이 ADR로 넘겼다.

- 이 서비스는 웹서비스다. 서버 코드는 배포하지 않지만 **브라우저로 보내는 코드는 배포에 해당**하고, 일부 라이선스(AGPL)는 **네트워크로 서비스하는 것만으로** 소스 공개 의무를 지운다.
- 수익화(W1)를 도입할 수 있으므로 상업 이용 제한 라이선스는 미래의 결정을 막는다.
- 패키지 하나가 다른 패키지 수백 개를 끌어오므로, 사람이 하나씩 확인할 수 없다.
- 지금까지 선택한 부품의 라이선스: Next.js·React·Tailwind CSS·Better Auth·Vitest·ESLint·Prettier(MIT), Lucide(ISC), Playwright·TypeScript(Apache-2.0), Pretendard(OFL-1.1). 모두 아래 허용 목록에 든다.

## Decision

### 1. 허용 — 고지만 하면 사용

| SPDX 식별자 | 비고 |
|---|---|
| `MIT` · `ISC` · `0BSD` | |
| `BSD-2-Clause` · `BSD-3-Clause` | 3-Clause는 저작자 이름의 홍보 이용 금지 |
| `Apache-2.0` | 수정한 파일이 있으면 변경 표시. NOTICE 파일이 있으면 함께 고지 |
| `OFL-1.1` | 서체 전용. 서체 단독 판매 금지 |
| `CC0-1.0` · `Unlicense` | 조건 없음 |
| `CC-BY-4.0` | 데이터·문서류(예: 브라우저 지원 데이터). 출처 표시 |

### 2. 조건부 — 쓰기 전에 검토하고 예외로 등록

| SPDX 식별자 | 검토 기준 |
|---|---|
| `MPL-2.0` | 해당 패키지 파일을 수정하지 않고 쓰는지 |
| `LGPL-2.1` · `LGPL-3.0` | 서버에서 수정 없이 동적으로 쓰는지, 브라우저 번들에 들어가지 않는지(예: 이미지 처리 `sharp`의 네이티브 라이브러리) |
| 위 목록에 없는 허용형으로 보이는 라이선스 | 조문을 읽고 허용형이 맞는지 |

예외는 `docs/quality/license-audit.md`에 **패키지명·버전·라이선스·괜찮은 이유·확인일**을 기록하고, CI 검사 설정의 예외 목록에 패키지 단위로 등록한다. 라이선스 전체를 허용 목록에 올리지 않는다.

### 3. 금지

| 라이선스 | 이유 |
|---|---|
| `GPL-2.0` · `GPL-3.0` | 브라우저로 보내는 코드에 섞이면 소스 공개 의무 |
| `AGPL-3.0` | 웹서비스로 제공하기만 해도 서버 코드까지 소스 공개 의무 — **이 서비스에 가장 위험** |
| `SSPL` · `BUSL`(Business Source) · Elastic License 등 | 오픈소스가 아니며 상업 이용 제한(W1과 충돌) |
| `CC-BY-NC-*` 등 비상업 조건 | 상업 이용 금지(W1과 충돌) |
| 라이선스 없음·`UNLICENSED`·식별 불가 | 허락이 없으면 이용 권리가 없다 |

### 4. 적용 범위와 실행

- **런타임 의존성과 개발용 의존성(테스트·빌드 도구)에 같은 목록을 적용한다.** 1인 운영에서 목록을 둘로 나누면 혼동이 크다. 개발용 도구가 막히면 §2 절차로 예외 등록한다.
- 직접 설치한 패키지뿐 아니라 **그 패키지가 끌어오는 하위 패키지 전부**를 검사한다.
- CI(ADR 0033)에서 허용 목록 + 예외 목록 외의 라이선스가 발견되면 **실패**한다. 도구 선택은 10단계.
- 허용·예외 패키지의 저작권·라이선스 문구로 리포 루트 `THIRD_PARTY_NOTICES`를 **자동 생성**하고, 서비스의 "오픈소스 고지"(`/help` 하단)에 게시한다(1차 감사 §3).
- 외부 서비스(Vercel·Supabase·카카오)의 이용약관은 의존성 라이선스가 아니므로 이 ADR 범위 밖이다(9단계 ⑨ 처리위탁 기재).

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 금지 목록만 두기(나머지 전부 허용) | 처음 보는 라이선스·라이선스 불명이 조용히 통과한다 |
| 런타임·개발용 목록 분리 | 법적으로는 더 정밀하지만 1인 운영에서 관리가 헷갈린다. 예외 등록으로 충분하다 |
| GPL 계열을 개별 검토로 허용 | 브라우저 번들 여부를 매번 판단해야 하고, 실수 시 비용이 크다 |
| 수동 감사만(CI 없음) | 하위 패키지 수백 개를 사람이 확인할 수 없다 |

## Consequences

- (+) 코드 공개 의무·상업 제한이 있는 부품이 들어오는 순간 CI가 막아, 나중에 빼내는 공사를 예방한다.
- (+) 지금까지 선택한 부품은 모두 허용 목록이라 바꿀 결정이 없다.
- (+) 고지 파일이 자동 생성되어 허용 라이선스의 고지 의무를 지킨다.
- (−) 새 패키지가 처음 보는 라이선스를 끌어오면 CI가 막혀 확인 작업이 생긴다.
- (−) 패키지가 적어 둔 라이선스 정보가 틀린 경우가 있어, 출시 전 최종 감사에서 주요 패키지는 실제 LICENSE 파일을 다시 확인한다.
- 1차 감사 §4의 "의존성 라이선스 감사, 허용/금지 라이선스 ADR — 9단계(2차)" 항목은 이 ADR로 닫는다. 패키지 전수 목록은 10단계에서 CI가 만든다.
