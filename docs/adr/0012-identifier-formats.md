# 0012. 식별자 형식 확정 — 시향기 슬러그·닉네임 자동 생성·프로필 공개 식별자

- Status: **Accepted** (2026-09-11 확정)
- 관련 문서: [0005-seo-slug-urls.md](./0005-seo-slug-urls.md), [0008-anonymized-retention-on-withdrawal.md](./0008-anonymized-retention-on-withdrawal.md), [05-data-model.md](../05-data-model.md) §3.7 E6·E9, [04-wireframes.md](../04-wireframes.md) §7

## Context

ADR 0005는 콘텐츠 URL에 SEO 슬러그를 쓰기로 하면서, 아래 세 가지 세부 형식은 "6단계 ERD에서 확정"으로 명시적으로 미뤄뒀다.

1. **시향기 슬러그의 소스** — 시향기는 한 줄 요약(제목)이 없는 서비스 설계([ADR 0004](./0004-single-page-writing-form.md))라, 브랜드·향수·계열처럼 표시명에서 슬러그를 뽑을 소스가 없다.
2. **작성자 프로필(`/users/:id`)의 공개 식별자 형식** — 05-data-model.md §2.9가 "내부 id를 그대로 노출하지 않는 값"이어야 한다고만 정해뒀고, 형식은 열려 있었다.
3. **일반 닉네임 자동 생성 규칙** — 04-wireframes.md §7이 "익명 표시명 `user_NNNNNN`(ADR 0008)과 네임스페이스가 겹치지 않아야 한다"는 제약만 남기고 6단계로 미뤘다.

공개 URL과 표시 데이터는 한번 사용자에게 노출되면 바꾸기 어렵다(ADR 0005 Context와 동일한 이유). ERD 착수 시점에 정해야 스키마(컬럼 길이·문자셋·유니크 제약)가 흔들리지 않는다.

## Decision

### 1. 시향기 슬러그 — 순수 랜덤 코드

향수·브랜드 슬러그와 무관한 **짧은 랜덤 문자열**을 사용한다. 예: `/reviews/8f3k2a1x`

- 향수 슬러그를 접두로 붙이는 하이브리드안(`/reviews/chanel-no5-9f2a`)은 채택하지 않는다. 시향기 수정 시 향수 자체는 바뀌지 않지만(§3.2 "수정 시 향수 변경 불가"), 구현이 한 단계 더 복잡해지는 데 비해 SEO 이득이 크지 않다고 판단했다.
- 유니크 제약은 **소프트 삭제 상태와 무관하게 테이블 전체**에 건다. 완전 삭제(보관기간 경과, ADR 0011) 전까지는 삭제된 글의 슬러그도 계속 점유되지만, 랜덤 코드라 재사용 압박이 없고, "삭제 예정 글의 슬러그가 다른 새 글에 재할당되는" 사고를 원천 차단한다. 이것으로 ADR 0011 Consequences가 남긴 "슬러그 유니크 제약 충돌" 문제를 해소한다.

### 2. 작성자 프로필 공개 식별자 — 랜덤 짧은 코드

`/users/:id`의 `:id`는 **내부 사용자 id와 무관한 랜덤 코드**를 쓴다. 예: `/users/k3f9a2x1`

- 순차 정수안은 기각한다. 민감 정보는 아니지만, 가입 순서·전체 회원 수가 URL만으로 드러나는 것을 피한다.
- 시향기 슬러그와 같은 생성 방식(랜덤 코드)을 써서 구현을 통일한다.

### 3. 일반 닉네임 자동 생성 — 형용사 + 향 관련 명사 조합

최초 로그인 시 서비스 닉네임을 **형용사 + 향 관련 명사** 조합으로 자동 생성한다. 예: "설레는 베르가못", "차분한 머스크", "엉뚱한 시더우드"

- "재미있게 쓰도록 유도하는 것이 최대 관심사"(§확정 정책)라는 서비스 톤에 맞춘다. 무작위 영숫자 조합(예: `guest_7f3k29`)보다 사용자가 처음 받는 닉네임부터 서비스 컨셉을 전달한다.
- 형용사·명사 풀은 **사람이 쓴 고정 문구 목록**이다(W9 무-AI 정책과 동일한 원칙 — 목록 확장은 DB 데이터 추가로, 배포 불필요).
- 접두사 `user_`는 사용하지 않는다 — 탈퇴 시 발급되는 익명 표시명 `user_NNNNNN`(ADR 0008)의 네임스페이스와 절대 겹치지 않도록, 이 접두사는 익명 표시명 전용으로 예약한다.
- 조합 충돌(동일 조합 재생성) 시 재시도하여 유니크를 보장한다. 사용자가 이후 닉네임을 직접 바꿀 수 있으므로(§3.3), 자동 생성값은 초기값일 뿐이다.

## 검토한 대안

- **시향기 슬러그 하이브리드안**(향수 슬러그 + 랜덤 접미사): ADR 0005가 재검토 여지로 남겼던 안. URL만 봐도 어떤 향수인지 드러나 SEO·공유 미리보기에 유리하지만, 향수 슬러그가 바뀌면(브랜드·향수명 정정 등) 이미 공유된 시향기 URL도 함께 무효화할지 결정해야 하는 부담이 추가된다. 순수 랜덤 코드는 향수 슬러그 변경과 완전히 독립적이라 더 안정적이라 채택.
- **프로필 식별자로 순차 정수**: 구현은 가장 단순하지만, 05-data-model.md가 이미 "내부 id를 그대로 노출하지 않는 값"을 요구했고, 순차 정수는 내부 id와 본질적으로 같은 정보(생성 순서)를 노출한다. 기각.
- **닉네임 무작위 영숫자 조합**: 구현이 가장 단순하지만 서비스 톤과 어울리지 않고, `user_` 접두사를 피하면서도 `guest_`류 접두사를 쓰면 시각적으로 익명 표시명과 여전히 헷갈릴 수 있어 기각.

## Consequences

- (+) ADR 0005가 미결로 남긴 URL 형식 질문 세 가지가 모두 해소되어 6단계 ERD가 막힘없이 진행된다.
- (+) 시향기·프로필 식별자가 같은 방식(랜덤 코드)이라 슬러그 생성 로직을 하나로 통일할 수 있다.
- (+) 자동 생성 닉네임이 서비스 컨셉을 강화한다("향수가 사람이라면?" 톤과 일치).
- (−) 시향기 URL만으로는 어떤 향수의 시향기인지 드러나지 않는다(순수 랜덤 코드 선택의 트레이드오프). 페이지 자체의 title·메타(§2.8 SEO 메타)가 이를 보완한다.
- (−) 닉네임 자동 생성용 형용사·명사 어휘 풀을 관리자가 유지보수해야 한다(질문 카드 문구·placeholder 풀과 같은 성격의 운영 부담, E16·E17과 유사한 신규 테이블 필요).
- (−) 랜덤 코드 생성 시 충돌 검사(유니크 재시도) 로직이 시향기 등록·프로필 발급·닉네임 생성 세 곳 모두에 필요하다.
