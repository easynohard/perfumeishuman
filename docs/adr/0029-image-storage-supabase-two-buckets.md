# 0029. 향수 이미지·브랜드 로고는 Supabase Storage에 두고, 서버를 거쳐 올리며, 공개·비공개 보관함 2개 + 짧은 캐시로 즉시 내린다

- Status: **Accepted** (2026-11-17 — 9단계 기술 스택 4번 결정, 사용자 승인)
- 관련 문서: [ADR 0009](./0009-perfume-image-sourcing-and-takedown.md)(이미지 조달·선조치) · [ADR 0026](./0026-nextjs-typescript-single-codebase.md) · [ADR 0027](./0027-hosting-vercel-db-supabase-seoul.md)(Vercel + Supabase 서울) · [legal/image-rights-and-takedown.md](../legal/image-rights-and-takedown.md) · [07-api-spec.md](../07-api-spec.md) §3.6·§4.4.3·§4.4.4·부록 A

## Context

07은 다음을 9단계로 넘겼다(부록 A·§3.6).

- 이미지·로고 파일을 어디에 저장할지
- 업로드 방식: 서버가 파일을 직접 받을지(multipart), 저장소에 직접 올리는 임시 주소를 발급할지. 이 선택이 `PUT /admin/perfumes/{slug}/image`·`POST·PATCH /admin/brands`의 요청 형식을 정한다
- 이미지를 비공개로 돌렸을 때 CDN·브라우저 캐시를 어떻게 무효화할지

조건:

- 이미지는 **관리자만** 올린다(사용자 업로드 없음, ADR 0009 §7). 양은 향수 수백 개 × 1장 + 브랜드 로고 수준이다.
- 이미지는 이미 누끼를 따서 정사각형으로 통일한 것이다(ADR 0009 §2). 파일 크기는 보통 1MB 이하다.
- 권리 이의가 접수되면 **비공개 조치 72시간 이내, 목표 24시간**이다(ADR 0009 §4). 비공개분은 이의가 해소되면 되살릴 수 있어야 하고, 영구 제거(`removed`)는 되돌릴 수 없다(07 §4.4.3).
- 이미지가 없으면 텍스트 카드로 폴백한다(ADR 0009 §5). 공개 응답은 비공개 이미지를 `image: null`로 내려준다(07 §4.1).
- 운영자는 1인·첫 개발이다. 새 업체·계정·비밀값이 늘어나는 것을 비용으로 본다.

2026-11-17 기준으로 확인한 사실(재확인 필요):

- Supabase Storage는 모든 플랜에 기본 CDN을 제공하고, 캐시 유지 시간은 업로드 시 지정하는 `cacheControl`을 따른다.
- 파일 변경·삭제 시 CDN 캐시를 자동으로 무효화하는 **Smart CDN**과 수동 **캐시 삭제(purge)** 기능은 **Pro 플랜 이상**이다. 반영까지 최대 약 60초 걸리며, 브라우저 캐시는 지우지 못한다.
- Vercel 함수는 요청 본문 크기 상한이 약 4.5MB다.

## Decision

### 1. 저장 장소 — Supabase Storage (ADR 0027의 서울 프로젝트)

ADR 0027에서 보류한 Supabase Storage를 채택한다. 보관함(bucket)을 2개 둔다.

| 보관함 | 공개 여부 | 담는 것 |
|---|---|---|
| 공개 보관함 | 누구나 URL로 읽기 가능 | 지금 화면에 보여도 되는 이미지·로고만 |
| 비공개 보관함 | 서버만 접근 | 등록된 모든 이미지·로고의 원본 |

쓰기는 두 보관함 모두 **서버만** 한다. 브라우저에서 보관함에 직접 쓰지 않는다.

### 2. 업로드 — 관리자 → 우리 서버 → 보관함 (multipart)

- 관리자 화면이 파일과 메타데이터(`source_url`·`alt` 등)를 **한 요청(multipart/form-data)** 으로 서버에 보낸다. `PUT /admin/perfumes/{slug}/image`·`POST·PATCH /admin/brands`의 파일 전달 방식은 이것으로 확정한다.
- 서버가 출처 URL 유무·이미지 형식·크기를 한곳에서 검사한 뒤 두 보관함에 저장한다.
- 파일 크기 상한은 **약 2MB**로 둔다(Vercel 본문 상한 4.5MB 안쪽). 정확한 값과 허용 형식은 구현 단계에서 정한다.
- 저장 파일 이름은 매번 새로 만든다(예: 무작위 문자열). 교체·복원 시 같은 이름을 다시 쓰지 않아 오래된 캐시와 섞이지 않는다.

### 3. 비공개·복원·영구 제거

| 조치 | 공개 보관함 | 비공개 보관함 |
|---|---|---|
| 비공개(`hidden`·`disputed` 등 `normal`이 아닌 상태) | **삭제** | 유지 |
| 브랜드 일괄 비공개 | 해당 브랜드 이미지 전부 삭제 | 유지 |
| 복원(`normal`로 되돌림) | 원본을 **새 파일 이름**으로 다시 복사 | 유지 |
| 영구 제거(`removed`) | 삭제 | **삭제** |

- 공개 보관함에서 지우므로, 옛 URL을 아는 사람도 캐시가 만료된 뒤에는 이미지를 볼 수 없다.
- 이미지 상태를 바꾸면 그 향수(또는 브랜드)가 나오는 페이지의 서버 캐시도 즉시 갱신해, 화면이 바로 텍스트 카드로 바뀌게 한다. 구체 방식은 구현 단계에서 정한다.

### 4. 캐시 — 유지 시간 1시간

- 공개 보관함 파일의 캐시 유지 시간(`cacheControl`)을 **1시간(3600초)** 으로 둔다.
- 무료 플랜에서는 캐시를 즉시 지울 수 없으므로, 비공개 처리 후 CDN·브라우저에 남은 사본은 **최대 1시간 안에** 사라진다. ADR 0009의 목표(24시간)를 충분히 지킨다.
- Supabase를 Pro로 전환하면 Smart CDN의 자동 무효화(약 60초)도 함께 쓴다. 브라우저 캐시는 그때도 1시간 규칙에 따른다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| Vercel Blob | Vercel 화면에서 관리할 수 있지만 보관 업체가 하나 늘어나고, 연결·비밀값·처리방침 기재가 늘어난다 |
| Cloudflare R2 | 전송량이 무료라 트래픽이 커지면 유리하다. 하지만 계정·설정이 하나 더 생기고 지금 규모(수백 장)에서는 이점이 없다. **이미지 트래픽이 커지면 1순위 이전 후보**로 남긴다 |
| AWS S3 + CloudFront | 즉시 캐시 삭제 등 기능은 충분하지만 권한·네트워크 설정이 복잡해 초보 1인에게 부담이 크다 |
| 저장소에 직접 올리는 임시 주소(signed upload URL) 발급 | 큰 파일에 유리하지만 "주소 발급 → 업로드 → 등록 확정" 단계가 늘어나고 검사가 두 곳으로 나뉜다. 이미지가 작아 필요 없다 |
| 보관함 1개 + 비공개 시 파일 이동 | 동작은 같지만 "지금 보여도 되는 것"과 "원본"의 구분이 보관함 단위로 드러나지 않아 실수 위험이 크다 |
| 보관함 1개(비공개) + 서명된 URL로 보여 주기 | 비공개 효과는 확실하지만 URL이 계속 바뀌어 캐시를 쓰기 어렵고 페이지가 느려진다 |

## Consequences

- (+) 새 업체·계정·비밀값·처리위탁 항목이 늘지 않는다. DB와 같은 Supabase 프로젝트에서 관리한다.
- (+) 업로드 검사가 서버 한곳에 모이고, 07의 "파일 + 출처 URL 한 요청" 설계와 그대로 맞는다.
- (+) 비공개 시 공개 보관함에서 실제로 지우므로 옛 URL이 계속 살아 있는 문제가 없다. 원본은 남아 복원할 수 있다.
- (+) 비용 0원으로 24시간 목표를 지키고, Pro 전환 시 별도 이전 없이 즉시 무효화가 붙는다.
- (−) 비공개 처리 후 **최대 1시간** 동안은 일부 이용자에게 옛 사진이 보일 수 있다(목표 안이라 감수).
- (−) 캐시 유지 시간이 짧아 원본 요청이 상대적으로 많다. Supabase 무료 플랜의 전송량 한도를 ⑩ 비용 추정에서 확인한다.
- (−) 원본과 공개본이 두 보관함에 나뉘어 있으므로, 상태 변경 처리가 둘 중 한쪽만 성공하는 경우에 대비해 상태 변경 로직은 "DB 상태가 기준, 보관함은 그에 맞춘다"로 구현하고 주기 점검으로 어긋남을 보정한다(구현 단계).
- (−) 나중에 R2 등으로 옮기면 파일 복사와 URL 일괄 변경이 필요하다. 규모가 작아 큰 공사는 아니다.
- 이미지는 개인정보가 아니므로 저장 위치가 처리방침의 국외이전 판단에는 영향을 주지 않는다.
- 07 §3.6의 "캐시 무효화 방식은 9단계"와 부록 A의 업로드 방식 미결 항목은 이 ADR로 닫는다.
