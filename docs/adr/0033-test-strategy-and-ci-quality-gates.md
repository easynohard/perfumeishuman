# 0033. 테스트·품질 게이트는 검사 5종을 개발 진행 순서에 맞춰 단계적으로 켠다

- Status: **Accepted** (2026-11-17 — 9단계 기술 스택 7번 결정, 사용자 승인)
- 관련 문서: [01](../01-problem-definition-scope.md) N5(FCP 2.5초)·N10(WCAG AA)·N8(1인 운영) · [03](../03-sitemap-ia.md) FL1~FL4 · [ADR 0008](./0008-anonymized-retention-on-withdrawal.md) · [ADR 0009](./0009-perfume-image-sourcing-and-takedown.md) · [ADR 0011](./0011-soft-delete-reviews.md) · [ADR 0016](./0016-aggregate-update-and-soft-delete-scope.md) · [ADR 0026](./0026-nextjs-typescript-single-codebase.md) · [ADR 0028](./0028-login-kakao-better-auth-session.md) · [ADR 0030](./0030-one-review-rule-partial-unique-index.md) · [ADR 0032](./0032-css-tailwind-with-token-only-theme.md)

## Context

CLAUDE.md 품질·법무 트랙은 9단계에 "테스트 전략·품질 게이트 기준 ADR"을, 10단계에 CI 구현(lint·타입체크·단위/통합 테스트·커버리지·라이선스 검사·Lighthouse·접근성)을 두었다. 출시 전 관문은 "CI 품질 게이트 전부 통과(N5 FCP 2.5초·N10 WCAG AA 포함)"를 요구한다.

- 운영자는 1인·첫 개발이라 코드를 검토해 줄 사람이 없다. 한 기능의 수정이 다른 기능(특히 탈퇴·삭제 같은 법적 규칙)을 조용히 깨뜨려도 알아채기 어렵다.
- 일부 규칙은 DB 수준에서만 확인된다. 예: 동시 요청 시 1인 1향수 1시향기(ADR 0030 부분 유니크 인덱스).
- 카카오 로그인(ADR 0028)은 자동화된 브라우저가 통과할 수 없다.
- ADR 0032는 "색 값을 코드에 직접 적기 금지"의 자동 검사 여부를 이 결정으로 넘겼다.

## Decision

### 1. 검사 5종 — 모두 CI(GitHub Actions)에서 돌리고, 실패하면 반영하지 않는다

| # | 검사 | 도구 | 대상 |
|---|---|---|---|
| 1 | 문법·습관 검사 | ESLint + Prettier (Next.js 기본 구성) | 전체 코드. **색 임의 값(예: `bg-[#…]`) 금지 규칙 포함**(ADR 0032) |
| 2 | 타입 검사 | TypeScript (`tsc --noEmit`) | 전체 코드 |
| 3 | 기능 테스트 | Vitest + **실제 PostgreSQL**(CI에서 테스트용으로 띄웠다 지움) | 아래 §2 핵심 규칙 + 각 기능의 규칙 |
| 4 | 화면 흐름 테스트 | Playwright | FL1~FL4 4개 흐름만 |
| 5 | 속도·접근성 검사 | Lighthouse(CI) + axe | 주요 화면의 FCP(N5)·접근성(N10) |

라이선스 검사도 CI에 넣되, 허용/금지 기준은 ⑧ 라이선스 2차 ADR에서 정한다.

### 2. 기능 테스트에서 처음부터 필수인 핵심 규칙

틀리면 신뢰·법 문제가 되는 규칙은 해당 기능을 만들 때 테스트를 **반드시 함께** 만든다.

- 1인 1향수 1시향기 — 동시 요청에도 1건만 생성, 소프트 삭제 후 재작성 가능(ADR 0023·0030)
- 추천 1인 1회·취소 시 집계 감소(ADR 0016)
- 소프트 삭제분이 관리자 화면 외 목록·피드·검색·SEO·집계에 나오지 않음(ADR 0011·0016)
- 탈퇴 시 개인정보 파기 + 글·추천 보존 + `user_NNNNNN` 익명 표시(ADR 0008)
- 비공개·제거 이미지는 공개 응답에서 `image: null`(ADR 0009)
- 비로그인 사용자의 쓰기·추천 차단(ADR 0014)

### 3. 켜는 순서

| 시점 | 켜는 검사 |
|---|---|
| 10단계 프로젝트 생성 시 | 1 문법, 2 타입 |
| 기능 개발 시작 시 | 3 기능 테스트(기능마다 함께 작성) |
| 주요 화면이 갖춰졌을 때 — 늦어도 출시 전 | 4 화면 흐름, 5 속도·접근성 |

출시 전 관문에서는 5종 모두 켜져 있고 통과해야 한다.

### 4. 화면 흐름 테스트의 로그인

자동화된 브라우저는 카카오 로그인을 통과할 수 없으므로 **테스트 환경에서만 켜지는 테스트용 로그인**을 둔다. 이 경로는 환경 설정으로 테스트 환경에서만 활성화하고, 프로덕션에서는 **코드 경로 자체가 동작하지 않도록** 막는다(이 차단도 테스트한다).

### 5. 숫자 기준은 10단계에서

- 커버리지 임계치, Lighthouse·접근성 점수 기준값은 CLAUDE.md 방침대로 **10단계에서 코드를 보며** 정한다. 그전까지 커버리지는 측정·표시만 한다.
- N5 "모바일 3G 기준 FCP 2.5초"는 Lighthouse 기본 모바일 조건(느린 4G)과 다르므로, **3G 조건으로 직접 설정해 측정**하는 것을 원칙으로 한다. 구체 수치 설정은 10단계.
- 문서화(`docs/quality/test-strategy.md`·`ci-quality-gates.md`)는 기준값과 함께 10단계에서 만든다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 자동 테스트 없이 수동 확인 | 1인이 매번 전부 확인할 수 없고, 법적 규칙이 조용히 깨질 위험이 크다 |
| Jest(Vitest 대신) | 오래 쓰였지만 TypeScript·ESM 설정이 Vitest보다 번거롭다 |
| DB를 흉내 내는 가짜 객체(mock)로만 기능 테스트 | 부분 유니크 인덱스·트랜잭션 같은 DB 동작을 확인할 수 없다 |
| 화면 흐름 테스트를 넓게 | 느리고 자주 깨져 1인 유지보수가 어렵다. 규칙 검증은 3번이 맡는다 |
| 처음부터 높은 커버리지 숫자 강제 | 숫자를 채우기 위한 의미 없는 테스트가 늘기 쉽다. 핵심 규칙 목록 필수가 더 효과적이다 |

## Consequences

- (+) 혼자 개발해도 수정마다 자동 검토가 붙어, 핵심 규칙과 출시 전 관문(N5·N10)을 확인할 수단이 생긴다.
- (+) 1·2번은 Next.js 기본 구성이라 추가 비용이 거의 없다. GitHub Actions는 무료 한도 안에서 시작한다(⑩ 비용 추정에서 확인).
- (+) 실제 PostgreSQL로 테스트해 ADR 0030의 동시 요청 방어를 그대로 검증한다.
- (−) 도구가 늘어 10단계 초기 설정 작업이 생긴다.
- (−) 테스트용 로그인 경로는 잘못 열리면 보안 사고가 되므로 차단 테스트와 리뷰가 필수다.
- (−) 화면 흐름·속도 검사는 CI 시간이 길다. 필요하면 PR마다가 아니라 `dev/minwoo` → `main` 반영 시점 등으로 실행 범위를 조정한다(10단계).
