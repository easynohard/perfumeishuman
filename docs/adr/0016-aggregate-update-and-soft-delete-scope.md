# 0016. 집계 컬럼은 애플리케이션 증감 + 주기 보정, 소프트 삭제 제외는 기본 스코프

- Status: **Accepted** (2026-10-01 확정)
- 관련 문서: [0008-anonymized-retention-on-withdrawal.md](./0008-anonymized-retention-on-withdrawal.md), [0011-soft-delete-reviews.md](./0011-soft-delete-reviews.md), [06-erd.md](../06-erd.md) §3·§4

## Context

6단계가 집계 컬럼 6종(`perfume.post_count`, `perfume.total_recommend_count`, `brand.perfume_count`, `accord.perfume_count`, `user.post_count`, `user.received_recommend_count`)의 위치·이름을 확정하면서, **갱신 방식**과 **소프트 삭제 조회 제외 방식**을 7단계로 넘겼다(`06-erd.md` §4). 추천 버튼의 카운트는 누른 즉시 반영되어야 하고, ADR 0011은 삭제분을 "관리자 화면 외 모든 목록·피드·검색·SEO·집계에서 제외"하도록 요구한다. 운영 규모는 1인 운영, 향수 100~300개 수준의 소규모다.

## Decision

### 1. 집계 컬럼 갱신: 애플리케이션 증감 + 주기 보정

- 쓰기 연산이 **같은 트랜잭션 안에서** 관련 집계 컬럼을 증감한다. DB 트리거는 쓰지 않는다.
- **주기적 재계산(예: 하루 1회)** 으로 실제 `COUNT` 결과와 비교해 어긋난 값을 보정한다. 증감 로직의 버그나 장애로 생긴 불일치를 되돌리는 안전망이다.
- 갱신 대상 이벤트:
  - 시향기 등록 / 소프트 삭제(본인·관리자): `perfume.post_count`, `user.post_count`, 그리고 해당 시향기가 받은 추천만큼 `perfume.total_recommend_count`, `user.received_recommend_count`
  - 추천 / 추천 취소: `post.recommend_count`, `perfume.total_recommend_count`, `user.received_recommend_count`
  - 향수 등록 / 삭제: `brand.perfume_count`, `accord.perfume_count`
- **탈퇴는 집계를 갱신하지 않는다.** ADR 0008에 따라 시향기와 추천이 그대로 보존되고 탈퇴자가 누른 추천의 카운트도 유지된다.
- 소프트 삭제된 시향기는 집계에서 제외되어야 하므로(ADR 0011), 삭제 시 위 카운트를 감소시킨다.

### 2. 소프트 삭제 조회 제외: 기본 스코프

- 시향기 조회 계층이 `delete_status`로 삭제분을 **항상 기본 필터링**한다(기본 스코프). DB 뷰는 쓰지 않는다.
- 삭제분을 읽는 경로는 관리자용으로 **이름을 명시적으로 분리**한 조회 메서드 하나로 제한한다.
- 목록·피드·검색·SEO·집계 어디에도 삭제분이 새지 않는다는 점을 **자동 테스트로 검증**한다(품질 게이트 대상, 10단계).
- 7단계 API 명세에는 "관리자 API 외의 어떤 응답에도 삭제분이 없다"는 규칙으로 명시한다. 기본 스코프의 구체 구현 방식은 ORM 등 스택에 의존하므로 9·10단계에서 확정한다.

## 검토한 대안

- **DB 트리거로 집계 갱신**: 로직이 DB 안에 숨어 테스트·디버깅이 어렵고, 스택 확정(9단계) 전이라 기각.
- **주기 재계산만 사용**: 추천 직후 카운트가 즉시 오르지 않아 UX가 나빠져 기각.
- **컬럼 없이 읽을 때마다 `COUNT`**: 이 규모에서는 가능하나 6단계에서 컬럼을 이미 확정했으므로 기각.
- **소프트 삭제 제외를 DB 뷰로 구현**: 필터 누락이 구조적으로 불가능하다는 장점이 있으나 뷰 관리가 늘고 ORM과의 궁합이 스택에 따라 나빠질 수 있어 기각. 필터 누락 위험은 자동 테스트로 대응한다.

## Consequences

- (+) 추천·등록·삭제 직후 카운트가 정확하게 반영되고, 불일치가 생겨도 보정 배치가 복구한다.
- (+) 로직이 애플리케이션 코드에 있어 단위·통합 테스트로 검증할 수 있다.
- (−) 집계를 갱신하는 모든 쓰기 경로에서 증감 누락이 생길 수 있다 → 7단계 API 명세에 엔드포인트별 갱신 대상을 명시하고, 보정 배치와 테스트로 방어한다.
- (−) 보정 배치를 10단계에서 구현·운영해야 한다. ADR 0011의 보관기간 경과분 완전 삭제 배치와 함께 관리한다.
- (−) 기본 스코프는 직접 작성한 쿼리에서 필터를 빠뜨릴 수 있다 → 조회는 반드시 조회 계층을 통하도록 컨벤션으로 정하고(10단계), 삭제분 노출 방지 테스트를 CI 게이트에 포함한다.
- (−) 시향기 소프트 삭제의 복구 기능 여부는 확인되지 않았다. 복구를 두게 되면 증가 방향의 갱신도 같은 방식으로 처리한다.
