# 0011. 시향기 삭제는 소프트 삭제 + 처리 이력으로 한다

- Status: **Accepted** (2026-08-31 확정)
- 관련 문서: [05-data-model.md](../05-data-model.md) §0 결정 3 / §4 상태값 / §5.3 파기 기준, [02-user-stories.md](../02-user-stories.md) D2·E1·E3, [0008-anonymized-retention-on-withdrawal.md](./0008-anonymized-retention-on-withdrawal.md)

## Context

시향기 삭제에는 성격이 다른 세 경로가 있고, 각각 다른 요구를 건다.

- **본인 삭제** (D2): "삭제된 글은 목록·피드에서 사라진다." 사용자 기대는 "지우면 없어진다"이다.
- **관리자 삭제** (E1): "관리자의 삭제는 일반 삭제와 구분되어 기록된다(사유 메모 가능)." 무엇을 왜 지웠는지가 남아야 한다.
- **신고 처리** (E3): 관리자가 신고를 "삭제 처리"하면, 그 신고 건과 삭제가 이어져 추적 가능해야 한다.

시향기는 추천(E13)·신고(E14)가 참조하는 대상이기도 하다. 물리 삭제하면 참조 레코드가 함께 사라지거나 끊어져, **어떤 글에 대한 신고였는지 알 수 없는 처리 이력**만 남는다. 관리자가 악성 글을 지운 뒤 작성자가 이의를 제기하면 대조할 원본이 없다는 문제도 있다.

5단계 데이터 항목 확정 시점이고, 삭제 방식은 **모든 조회 쿼리의 형태를 바꾸는 결정**이라 나중에 바꾸면 전면 수정이 된다.

## Decision

**시향기는 소프트 삭제하고, 삭제 처리 이력을 함께 남긴다.**

### 1. 시향기에 두는 항목

- 삭제 상태 · 삭제 시각
- **처리 주체**: 본인 / 관리자 (E1의 "구분되어 기록된다"를 이 필드 하나로 충족)
- 삭제 사유 메모 (관리자 삭제 시)

관리자 조치는 이와 별개로 **관리자 조치 로그**(05-data-model §3.7 E15)에도 남긴다 — 시향기 자체가 완전 삭제된 뒤에도 조치 사실은 남아야 하기 때문이다.

### 2. 조회 규칙

삭제된 시향기는 **홈 피드·향수 상세·작성자 프로필·MY·검색·시향기 상세·SEO 색인에서 모두 제외**한다. 예외는 관리자 화면뿐이다. 집계값(추천 수·시향기 수)에서도 제외한다.

### 3. 보관 후 완전 삭제

소프트 삭제는 영구 보존이 아니다. 보관기간이 지나면 완전 삭제한다.

| 구분 | 보관기간 | 목적 |
|---|---|---|
| 본인 삭제 | 30일 (제안) | 오삭제 대응. 사용자 기대("지우면 없어진다")를 해치지 않도록 짧게 |
| 관리자 삭제 | 1년 (제안) | 이의·분쟁 대응 |

숫자는 개인정보처리방침에 그대로 실리므로 **05-data-model.md §8-2에서 확정**한다.

### 4. 탈퇴와의 관계

탈퇴는 삭제가 아니다. [ADR 0008](./0008-anonymized-retention-on-withdrawal.md)에 따라 탈퇴 회원의 시향기는 **삭제되지 않고 익명 처리되어 남는다.** 두 메커니즘은 독립적이며, "글을 지우고 싶으면 탈퇴 전에 직접 삭제하라"는 탈퇴 모달의 안내(F3)가 이 둘을 잇는 지점이다.

## 검토한 대안

- **전부 물리 삭제**: 가장 단순하지만 E1의 "구분되어 기록된다"를 충족하기 어렵고, 신고 처리 이력이 대상을 잃으며, 오삭제에 대응할 수 없어 기각.
- **본인 삭제는 물리 삭제, 관리자 삭제만 로그**: 사용자 기대에 가장 정직하지만, 삭제된 글에 달렸던 추천·신고가 함께 사라지고 오삭제 복구가 불가능하다. 관리자 로그에 본문 스냅샷을 따로 넣어야 해서 결국 두 벌의 저장 경로가 생긴다. 기각 — 대신 **본인 삭제분의 보관기간을 짧게(30일)** 두어 이 안의 취지를 흡수했다.

## Consequences

- (+) E1·E3의 기록 요구를 스키마 한 벌로 충족한다.
- (+) 오삭제·이의 제기에 대응할 여지가 생긴다.
- (+) 추천·신고의 참조 무결성이 유지되어, 신고 처리 이력이 대상을 잃지 않는다.
- (−) **모든 조회에 삭제 제외 조건이 붙는다.** 한 곳이라도 빠뜨리면 지운 글이 노출된다 — 기본 스코프·뷰 등으로 실수를 구조적으로 막는 방법을 6단계에서 정한다.
- (−) 삭제 후에도 본문이 일정 기간 DB에 남는다. **개인정보처리방침에 보관기간을 명시**해야 하며, 사용자가 본문에 개인 정보를 적은 경우 즉시 파기 요청에는 관리자가 개별 대응한다(ADR 0008 Consequences와 동일).
- (−) 슬러그 유니크 제약과 충돌할 수 있다 — 삭제된 글의 슬러그가 자리를 계속 차지한다. 6단계 ERD에서 처리 방식을 정한다.
- (−) 완전 삭제를 실행할 주기 작업(배치)이 필요하다. 10단계 환경 세팅 항목으로 넘긴다.
