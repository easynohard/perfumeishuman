# 0030. 1인 1향수 1시향기는 화면 안내 + 서버 확인 + 부분 유니크 인덱스의 세 겹으로 지킨다

- Status: **Accepted** (2026-11-17 — 9단계 기술 스택 5번 결정, 사용자 승인)
- 관련 문서: [ADR 0023](./0023-one-review-per-user-per-perfume.md)(규칙) · [ADR 0011](./0011-soft-delete-reviews.md)(소프트 삭제) · [ADR 0016](./0016-aggregate-update-and-soft-delete-scope.md)(집계 증감) · [ADR 0027](./0027-hosting-vercel-db-supabase-seoul.md)(PostgreSQL) · [06-erd.md](../06-erd.md) §3·§4 · [07-api-spec.md](../07-api-spec.md) §4.3

## Context

ADR 0023은 "한 사람은 한 향수에 시향기를 1개만, 소프트 삭제분은 세지 않는다"를 정했고, 구현 방식과 동시 요청 처리를 9단계로 넘겼다(06 §4, 07 `POST /reviews`).

- 소프트 삭제된 행이 테이블에 남으므로 (`user_id`, `perfume_id`) 단순 UNIQUE 제약으로는 "삭제 후 재작성"을 허용할 수 없다.
- 서버가 "이미 쓴 글이 있는지" 확인만 하면, 같은 사용자의 요청 두 개가 거의 동시에 들어올 때(느린 네트워크에서 연타 등) 둘 다 확인을 통과해 글이 2개 생길 수 있다.
- 시향기가 새로 생기는 길은 `POST /reviews` 하나뿐이다. 수정 시 향수는 바꿀 수 없고(07 `PATCH /reviews/{slug}`), 소프트 삭제 복구는 MVP에 없다(07 부록 A).
- DB는 PostgreSQL이다(ADR 0027). PostgreSQL은 조건을 붙인 유니크 인덱스(부분 유니크 인덱스)를 기본 기능으로 지원한다.

## Decision

1. **화면 안내(1겹)**: 향수 응답의 `my_review_slug`가 있으면 "시향기 쓰기"에서 "이미 소개했어요"를 띄운다(ADR 0023 그대로).
2. **서버 확인(2겹)**: `POST /reviews`는 저장 전에 같은 사용자·같은 향수의 삭제되지 않은 시향기가 있는지 조회하고, 있으면 409 `ALREADY_REVIEWED`.
3. **DB 최종 방어(3겹)**: `post`에 **삭제되지 않은 행에만 적용되는 (`user_id`, `perfume_id`) 부분 유니크 인덱스**를 건다. 개념상 다음과 같다(조건식의 정확한 값은 `delete_status` 값 정의에 맞춰 구현 단계에서 쓴다).

   ```sql
   CREATE UNIQUE INDEX post_one_per_user_perfume
     ON post (user_id, perfume_id)
     WHERE <삭제되지 않음 조건>;
   ```

4. 동시 요청으로 2겹을 함께 통과해도 DB가 두 번째 저장을 거절한다(유니크 위반). 서버는 이 거절을 **409 `ALREADY_REVIEWED`로 바꿔** 응답한다. 사용자에게는 2겹에서 막힌 경우와 똑같이 보인다.
5. 시향기 저장과 집계 증가(`perfume.post_count`·`user.post_count` 등, ADR 0016)는 **한 트랜잭션**으로 묶는다. 저장이 거절되면 집계 증가도 함께 취소된다.
6. 소프트 삭제된 행은 인덱스 조건에서 빠지므로 삭제 후 같은 향수에 다시 쓸 수 있다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 서버 확인만(2겹만) | 동시 요청 시 중복 2건이 생길 수 있다 |
| 저장 전 잠금(행 잠금·advisory lock)으로 줄 세우기 | 막을 수는 있으나 코드가 복잡하고, 부분 유니크 인덱스가 같은 일을 더 간단하고 확실하게 한다 |
| 생성 컬럼 등으로 칸을 추가해 단순 UNIQUE로 표현 | 부분 인덱스가 없는 DB(MySQL 등)를 위한 우회법이다. PostgreSQL에서는 불필요하고 스키마만 늘어난다 |
| DB 방어만(2겹 생략) | 동작은 하지만, 흔한 경우까지 에러를 거쳐 처리하게 된다. 확인 조회는 싸고 의도가 코드에 드러나므로 둔다 |

## Consequences

- (+) 동시 요청을 포함해 중복이 DB 수준에서 원천 차단된다. 애플리케이션 코드에 실수가 있어도 규칙이 깨지지 않는다.
- (+) 컬럼 추가가 없어 06 ERD의 컬럼 구성과 `erd.png`가 그대로다. 인덱스 하나만 추가된다.
- (+) 같은 인덱스가 "내 시향기 조회"(`my_review_slug` 계산) 속도도 돕는다.
- (−) 서버는 DB의 유니크 위반 에러를 알아보고 409로 바꾸는 처리가 필요하다(구현 단계, 테스트 대상).
- (−) `delete_status`의 값 정의가 바뀌면 인덱스 조건도 함께 바꿔야 한다. 마이그레이션 시 함께 확인한다.
- 06 §3·§4와 07 `POST /reviews`의 "구현은 9단계" 표시는 이 ADR로 닫는다.
