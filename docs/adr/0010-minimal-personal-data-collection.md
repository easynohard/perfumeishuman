# 0010. 개인정보는 최소 수집한다 — 이메일 미수집, 신고자 IP 미저장

- Status: **Accepted** (2026-08-31 확정)
- 관련 문서: [05-data-model.md](../05-data-model.md) §0 결정 1·2 / §5 개인정보 항목표, [0002-open-reading-login-for-actions.md](./0002-open-reading-login-for-actions.md), [0008-anonymized-retention-on-withdrawal.md](./0008-anonymized-retention-on-withdrawal.md), [02-user-stories.md](../02-user-stories.md) C1·E3·F1·F3, [01-problem-definition-scope.md](../01-problem-definition-scope.md) M11·M12·N13

## Context

5단계 데이터 모델링에서 수집 항목을 확정해야 했고, "더 받을 수도 있는" 지점이 두 곳 있었다.

**① 소셜 로그인에서 어디까지 받을 것인가.** 공급자는 고유 회원번호 외에 이메일·프로필 이미지·닉네임을 함께 넘길 수 있다. 이메일이 있으면 약관 개정 고지·문의 응대·권리 침해 통보를 개별적으로 할 수 있다. 그러나 이 서비스에는 이메일이 필요한 기능이 없다 — 알림은 MVP 범위 밖(W3)이고, 소셜 로그인이라 비밀번호 복구 개념이 없으며, 공지는 서비스 내 게시로 처리된다. 카카오의 이메일은 **선택 동의 항목**이라 받더라도 비어 있을 수 있어, 있으나 마나 한 값에 분기 로직만 늘어난다. 무엇보다 [ADR 0008](./0008-anonymized-retention-on-withdrawal.md)은 탈퇴 시 식별 정보 **즉시 파기**를 못박았으므로, 수집 항목이 늘면 파기 대상과 그 검증 부담이 그대로 늘어난다.

**② 게스트 신고(E3)의 중복 제한을 무엇으로 판별할 것인가.** E3의 AC는 "로그인 없이도 신고 가능하되 동일 대상 중복 신고는 제한한다"이다. 게스트에게는 계정이 없으므로 판별 키가 필요하고, 통상적인 답은 IP다. 그런데 IP는 개인정보다. 신고 기능 하나 때문에 **전체 방문자를 대상으로 하는 개인정보 수집 항목**이 새로 생기고, 처리방침에 항목·목적·보관기간을 써야 하며, 공용 와이파이·모바일 캐리어 NAT 환경에서는 남의 신고가 내 신고를 막는 오탐이 생긴다.

## Decision

**개인정보는 서비스가 실제로 쓰는 것만 받는다.**

### 1. 소셜 로그인 수집 범위

- **수집**: 소셜 공급자 구분, 공급자 회원번호
- **미수집**: 이메일, 프로필 이미지, 실명, 생년월일, 성별, 연락처
- 공급자가 동의 화면에서 **닉네임을 함께 넘기더라도 저장하지 않는다.** 서비스 닉네임은 최초 로그인 시 자동 생성되므로(C1 AC), 공급자 닉네임은 쓰이지 않는 개인정보가 된다.
- 결과적으로 탈퇴 시 파기 대상은 **공급자 구분·공급자 회원번호·서비스 닉네임 3개**로 한정된다.

### 2. 신고자 식별

- **신고자 IP를 저장하지 않는다.**
- 게스트의 동일 대상 중복 신고는 **브라우저 로컬 기록**으로 막는다. 서버는 "같은 시향기에 단위 시간당 N건 초과 시 자동 보류" 같은 **대상별 총량 규칙**만 둔다.
- 멤버의 신고는 사용자 참조로 정확히 중복을 막는다.
- 캐시를 지우면 우회할 수 있다는 것을 알고 받아들인다. 신고는 **접수 자체가 조치가 아니라 관리자 판단의 입력값**이고(M9·E3), 최종 방어선은 관리자 수동 처리다. 초기 규모에서 조직적 허위 신고는 현실적 위협이 아니다.

### 3. 예외 — 인프라 접속 로그

웹서버·호스팅이 자동으로 남기는 접속 로그(IP·User-Agent)는 이 결정의 예외다. 서비스가 수집하는 것이 아니라 인프라가 기록하는 것이며, 장애·침해 대응이라는 별도 목적을 갖는다. **처리방침에 반드시 기재**하고, 보존기간은 9·10단계(스택·환경 확정)에서 정해 기간 경과 시 삭제한다.

## 검토한 대안

- **이메일까지 수집**: 개별 연락 수단을 얻지만, 쓰지 않는 개인정보를 보유하는 상태가 된다. 카카오 이메일은 선택 동의라 NULL을 허용해야 해 "있을 수도 없을 수도 있는 연락 수단"이 되며, 그 상태로는 어차피 전원 대상 고지 수단이 못 된다. 기각.
- **이메일 + 프로필 이미지**: 4단계 와이어프레임 16개 화면 어디에도 아바타 자리가 없다. 쓰지 않을 데이터가 확실하므로 기각.
- **신고자 IP 해시 저장**: 우회는 어려워지지만 해시해도 IP는 개인정보로 다뤄야 하고(재식별 가능), 처리방침 항목이 늘며 공용 IP 오탐이 남는다. 얻는 것(허위 신고 억제)이 MVP 규모에서 크지 않아 기각.
- **신고를 로그인 필수로 변경**: 중복 제한은 깔끔해지지만 E3 AC를 수정해야 하고, **권리 침해를 발견한 외부인**(ADR 0009의 신고 창구 이용자)이 가입 없이 알릴 경로가 `/help` 이메일만 남는다. 신고 문턱을 올리는 방향이라 기각.

## Consequences

- (+) 개인정보처리방침이 짧고 정직해진다. 수집 항목이 적을수록 유출 시 피해와 파기 검증 부담이 함께 줄어든다.
- (+) [ADR 0008](./0008-anonymized-retention-on-withdrawal.md)의 익명화가 단순해진다 — 파기 대상 3개를 지우고 상태를 바꾸면 끝난다.
- (+) 게스트 신고 때문에 전체 방문자 대상 개인정보 항목이 생기는 일을 피했다.
- (−) **개별 사용자에게 연락할 수단이 없다.** 약관 개정 사전 공지(F2 AC)를 이메일로 할 수 없으므로, **공지 방식을 "서비스 내 게시"로 약관에 명시**해야 한다 (8단계 `docs/legal/terms-of-service.md`). 이 조문이 빠지면 F2 AC가 성립하지 않는다.
- (−) 계정 문의(예: "내 글이 안 보인다")에 응대할 때 본인 확인 수단이 소셜 재로그인뿐이다.
- (−) 게스트 신고는 캐시 삭제로 우회 가능하다. 신고 급증 시 관리자 부담이 곧바로 커진다.
- (−) 나중에 이메일이 필요해지면 **기존 회원에게 소급 수집이 불가능**하다. 재동의 흐름을 새로 만들어야 한다.

## 재검토 트리거

- 알림·메일 기능 도입 검토 시 (W3)
- 조직적 허위 신고가 실제로 발생했을 때
- 수익화(W1) 도입 — 마케팅 수신 동의가 논의되는 시점
